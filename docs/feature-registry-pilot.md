# Feature registry and layout independence — pilot

The three pilot experiences use the same permanent IDs as HQ (brain-rv-road-trip-mayhem, brain-chess, brain-sudoku). Existing colon-separated resource IDs are preserved for Cabinet bookmarks. The public module public/assets/scripts/feature-registry.js is the single pilot metadata/route source used by the server policy, client label renderer and Cabinet build. Keep IDs stable when renaming or reorganizing.

On ordinary pages using nav.js, and in Teacher Cabinet, launch links are matched by local URL, with optional data-feature-id or existing data-resource-id. The label renderer handles late-added links, fetches public availability only once when a mapped link exists, and preserves link clickability for server-rendered previews. It does not authorize access or rewrite layouts. The actual gate is based on the target URL, not the page containing the link. Moving a tile needs no flag update. A URL change requires registry aliases and actual middleware matcher updates; the build checks pilot route coverage and files. If a page does not load shared nav or Cabinet code, import and initialize the feature-availability module explicitly. Status is a snapshot per page load; reloading gets new flags. The direct request gate reads flags independently.

Cabinet generation keeps the three pilot entries and their canonical metadata even if a Brain Arcade hub card is moved. Other resources continue using the existing build. Static home/subject tile text and artwork are not yet generated from the registry; no visual redesign performed. Future shared tile rendering and HQ metadata edits require a separate pass. The remaining 156 inventory entries are not wired to this pilot. Shared engines and multiplayer are excluded. No preview/production deployment, migration or runtime configuration performed. Run npm run test:feature-gate and npm run test:feature-registry, then the full build and Vercel HTTP/browser smoke tests before release.
